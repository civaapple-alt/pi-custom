# 提案：Agent 执行过程的观察模式（Observe Mode）

- 状态：M1 已落地（报幕指南生效中），M2 待启动
- 背景：pi 会话中的讨论（2026-10）

## 1. 问题

pi 的 agent loop 全自动执行：一次 LLM 请求 → 一批 tool 调用 → 下一次请求。过程中存在两个控制缺口：

1. **速度缺口**：执行很快，用户来不及观察每一步在做什么，等注意到时事情已经发生
2. **意图缺口**：模型经常不输出任何文字，只反复"思考 + 调工具"，最后给一个总结。过程对人是黑盒——看不到"这一步想干什么"

注意：本提案**不是**审批（approve）方向。目标是把过程变得**可观察、可跟上节奏**，而不是每一步都要人批准。

## 2. 核心设计判断

**观察单元 = 一次 LLM API 调用（一个 turn），不是单个 tool。**

理由：一次 API 响应中的多个 tool 调用共享同一个意图，是一个不可拆分的"步骤"。单独观察某个 tool 的调用参数，无法回答"模型这一步想做什么"。

这与 pi 的执行结构对齐：pi 的循环就是 turn 驱动的，`turn_end` 事件在 turn 边界触发，tool 调用按批次归属。

## 3. 方案（两层）

### 第 1 层：让模型自己报幕（提示词工程，立即可做）

**手段**：全局 context 文件 `~/.pi/AGENTS.md` 加指南：

> 每次要调用工具时，先用 1-2 句话说明：本步目标、将调用哪些工具、为什么。然后再发起调用。仅在有工具调用时需要，纯文字回答不用。

**理由**：turn 边界摘要的原料是"模型的叙述"。没有叙述，观察界面只能展示 tool 参数（JSON），人看了仍不理解意图。叙述让第 2 层的摘要变成人类可读的章节标题。

**代价**：每轮多少量输出 token；上下文 1M + 缓存命中的场景下成本可忽略。

**参考**：pstack 全量版 `show-me-your-work` skill 是同一思路，可单独借鉴（精选版 26 个未含）。

### 第 2 层：观察模式（扩展实现，需原型验证）

**形态**：不拦截执行，只减速到人可跟随的节奏。每个 turn 边界展示批次摘要：

```
── Step 3 ─────────────────────────
目标: 验证 pstack 文档改动是否生效
工具: bash(pi config | grep ...)   → 查扩展加载
      bash(pi -p --no-session ...) → 实测 skill 列表
──────────────────── [回车继续] [放行本 turn]
```

**信息源**：第 1 层的叙述文本 + 本批 tool 调用清单（扩展在 `turn_end` 事件均可获得）。

**交互**：
- 回车继续：人工节奏步进
- "放行本 turn"：跳到下一个 turn 边界（不打散本批）
- 全程无拒绝/修改能力（那是 approve 方向，本提案明确排除）

**技术可行性**：pi 扩展 API 已有 `turn_end` / `agent_before_settle` 可挂 turn 边界；`ctx.ui.select/confirm` 提供阻塞式对话框。

**未决风险**：运行中（非 idle 状态）弹阻塞对话框是否被允许——这决定形态：
- 若允许 → 按键步进模式
- 若不允许 → 退化为"慢速跟随"：每 turn 自动暂停 N 秒展示摘要后自动继续

需原型验证后确定。

## 4. 与 codemode 的交互

pi 的 codemode（模型写 JS 脚本在沙箱里批量驱动内部工具调用）对观察模式的影响，源码核实后的结论：**不破坏设计，且提供了 batch 级观察所需的内部可见性**。

### 4.1 Turn 粒度：暂停点变少但每个更大

codemode 把多次 API 往返压缩为 1 次调用，turn_end 暂停点变稀疏。但 codemode 脚本本身就是按意图分组的批次（写脚本时自然先确定"这一步干什么"），与提案"观察单元 = 一批"的判断更契合。代价：一个脚本内可能混多个子意图，需要批次内部可见性（见 4.2）补充。

### 4.2 批次内部可见性（关键发现）

- 嵌套调用**会触发 `tool_call` / `tool_execution_*` 事件，带 `parentToolCallId`**——"不出现在 transcript"指不落盘为独立条目，事件层完全可观测
- 脚本结束后，内部调用以 `nestedCalls` 形式**持久化在父 toolResult**（含 name/arguments/usage）

因此批次摘要可以展开内部：

```
── Step 3 ─────────────────────────────
目标: 侦察 pstack 上游结构（模型叙述）
工具: codemode
  ├─ read  cursor-plugins/pstack/plugin.json
  ├─ read  pstack/skills/show-me-your-work/SKILL.md
  └─ bash  curl api.github.com/... (star 数对比)
────────────────────────── [回车继续]
```

### 4.3 报幕指南需补充 codemode 规则

现有草案"每次调用工具前说明目标/工具/原因"对 codemode 会失效（调用的是 1 个 codemode，内部工具在脚本里）。补充规则：

> 用 codemode 做批量操作前，叙述覆盖整批：这批要做什么、涉及哪些工具。脚本首行注释写明目标。

### 4.4 时序细节（并入 M2 验证）

codemode 执行内部调用时 LLM 不在循环里，turn 边界弹暂停对话框时脚本已跑完——"等批次结束再暂停"天然成立。但**批内步进做不到**（脚本执行不经过模型），对批内的细粒度观察只能靠事件流做"实时渲染/事后回放"。M2 原型需确认 `parentToolCallId` 事件流的 UI 渲染效果。

## 5. 非目标

- ❌ 审批/拦截 tool 调用（approve 方向）——pi 扩展 API 其实支持（`tool_call` 事件可 block / 改参数 / terminate），但那是另一个提案
- ❌ 暂停/续播单条流（token 级暂停）——LLM API 底层不支持，见 pi-notes 相关讨论
- ❌ 改动 pi 核心——以扩展 + context 文件实现，保持可拆卸
